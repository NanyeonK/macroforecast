# API stability tiers

**This is the adopted policy for 1.0.** It is not yet implemented: this page
publishes what the package will promise, and the runtime changes that follow
from it are separate work, sequenced at the end. Nothing in `macroforecast`
behaves differently because this page exists.

Inventory: `docs/api_inventory.json` (generated by `tools/api_inventory.py`).

The split is deliberate: **the inventory supplies facts, this page supplies
policy.** `docs/api_inventory.json` records only what the package declares —
which submodule owns a name, whether it is a lazy export or a namespace, and
whether the entry docs reference it. It assigns no tier. The tiers below are a
promise about what the package will keep working, which is a judgement no
generator can make.

## The finding that shapes everything else

**The documentation already teaches submodule paths, not top-level aliases.**
Every `mf.*` reference in `README.md` and `docs/guide/getting_started.md`:

```python
from macroforecast.pipeline import Arm, EvalSpec, TargetSpec, pipeline_spec, run_pipeline

mf.configure
mf.__version__
mf.data.load_fred_md
mf.window.from_cutoffs
mf.preprocessing.preprocess_spec
mf.feature_engineering.feature_spec
mf.feature_engineering.marx_step
mf.models.list_model_specs
```

Six `mf.<submodule>.<name>` paths and a `macroforecast.pipeline` import — against
two top-level names, `mf.configure` and `mf.__version__`, both of which are
STABLE below. Meanwhile `mf.__all__` exports **376** supported names — **353**
lazy exports, every one of which already has a submodule home, plus the **23**
submodule namespaces themselves. (`dir(mf)` reports 379; the extra three are not
API and are separated out below.)

So the canonical shape is not in dispute — it is already written down and taught.
The top-level surface is what accumulated beside it.

## The decision, made

**The top-level alias surface is convenience, not a supported API.** That was the
one genuinely open question, and it is now settled in favour of the shape the
documentation already teaches.

Concretely, of the 353 lazy root exports, exactly one — `configure` — stays a
stable root name. The other **352** are convenience aliases for a canonical
submodule path, they do not enter the semantic-versioning contract at 1.0, and
they are removed on the schedule below.

The aliases being convenience does **not** demote the functions. Every one of the
352 keeps a canonical home that stays public; only the second way of spelling it
goes away.

## The 1.0 root surface

Twenty-five names, and the arithmetic is checkable against the inventory:

```python
mf.configure       # 1 lazy export
mf.__version__     # the special surface, outside __all__

mf.analysis                mf.forecast_analysis       mf.model_selection
mf.data                    mf.forecast_diagnostic     mf.models
mf.data_analysis           mf.forecasting             mf.output
mf.evaluation              mf.interpretation          mf.pipeline
mf.feature_analysis        mf.meta                    mf.preprocessing
mf.feature_diagnostic      mf.metrics                 mf.reporting
mf.feature_engineering     mf.model_ensemble          mf.tests
mf.filters                 mf.window
```

That is 24 of the 376 `__all__` names — `configure` plus the 23 namespaces —
which leaves the 352 aliases; `__version__` makes 25 root names in total. The
namespace objects are the navigation the docs already teach, so they are stable
root names and are not on any removal list.

## Tiers over the canonical symbols

The tiers apply to canonical paths, not to root aliases. Across the 23
namespaces the submodule `__all__` lists declare **808** public paths (759
distinct names: `feature_diagnostic` and `forecast_diagnostic` mirror
`feature_analysis` and `forecast_analysis` exactly, 48 paths, and `spec` is
declared by both `mf.data` and `mf.window` — the root map settles its canonical
home as `mf.data.spec`).

### STABLE — the documented entry points (15 paths)

```python
mf.configure                            # canonically mf.meta.configure
mf.__version__

mf.data.load_fred_md
mf.data.custom_dataset
mf.preprocessing.preprocess_spec
mf.feature_engineering.feature_spec
mf.feature_engineering.marx_step
mf.models.list_model_specs
mf.window.from_cutoffs

from macroforecast.pipeline import (
    Arm, TargetSpec, EvalSpec, pipeline_spec, run_pipeline,
    PipelineSpec, PipelineReport,
)
```

Everything the getting-started path uses, plus `custom_dataset` — the documented
bring-your-own-data entry point, with its own guide and reference page — and the
two types a caller necessarily touches, since `pipeline_spec` returns a
`PipelineSpec` and `run_pipeline` consumes one and returns a `PipelineReport`.

The promise: these do not move or change signature within 1.x. If one ever has
to move, it gets a `FutureWarning` naming the replacement for at least one minor
release before anything breaks.

### ADVANCED — public, canonical path is the submodule (688 paths)

Everything else declared in a submodule's `__all__`, except the two subsystems
below. This is the bulk of the package: `mf.models.*`, `mf.feature_engineering.*`,
`mf.window.*`, `mf.data.*`, `mf.preprocessing.*`, `mf.model_selection.*`,
`mf.model_ensemble.*`, `mf.forecasting.*`, `mf.evaluation.*`, `mf.metrics.*`,
`mf.tests.*`, `mf.filters.*`, `mf.output.*`, `mf.pipeline.*`, `mf.meta.*`,
`mf.analysis.*`, `mf.data_analysis.*`, `mf.feature_analysis.*`,
`mf.feature_diagnostic.*`, `mf.forecast_analysis.*`, `mf.forecast_diagnostic.*`.

Documented in the generated reference, safe to use, and reached through their
module. They follow semantic versioning at 1.0: no breaking change without a
major version, and a deprecation cycle before removal. The **top-level alias**
for the 352 is the redundant part — not the function.

### EXPERIMENTAL — contract still moving (105 paths)

- `mf.interpretation.*` (83 paths) — the attribution primitives got correctness
  oracles in the #446 audit (`tests/interpretation/test_attribution_oracles.py`,
  `test_shapley_oracles.py`). `anatomy`, `oshapley`, and the pipeline-level
  `anatomy_provider` / `oshapley_provider` / `precompute_anatomy` /
  `precompute_oshapley` surfaces are exercised only through a monkeypatched
  backend, which pins the wiring and not the numbers.
- `mf.reporting.*` (22 paths) — covered by smoke, formatting and rendering tests
  (`tests/reporting/`), so it is not untested; but nothing pins its table columns
  or figure return shapes as a contract.

Usable, public, and staying — they simply do not carry the 1.0 stability promise
until the missing oracles exist.

## Three non-API globals to remove — not a decision

These are not API and never were:

| symbol | actually | bound by |
|---|---|---|
| `mf.Any` | `typing.Any` | `from typing import Any` |
| `mf.annotations` | `__future__.annotations` | `from __future__ import annotations` |
| `mf.import_module` | `importlib.import_module` | `from importlib import import_module` |

All three are globals of `macroforecast/__init__.py` itself — imports the lazy
loader needs at root module scope. They are public in `dir(mf)`, absent from
`__all__`, and owned by no submodule. Removing them cannot break correct code,
because no correct code calls `mf.Any`.

An earlier revision of this page said they were "surfaced because a submodule
imported them at module scope", and attributed them to `mf.tests`, `mf.data` and
`mf.evaluation`. That was the old `dir()`-scanning inventory misreporting their
provenance; the rebuilt inventory records them as root globals.

```{admonition} Correction (2026-08-09): `Split` was misclassified here
:class: important

An earlier revision of this page listed `mf.Split` in the table above as "a
builtin". That was wrong, and the inventory this page is built from said so:

    "name": "Split", "canonical": "mf.window.Split", "kind": "GenericAlias"

`Split` is a public type alias of the window subsystem. Its *top-level* alias is
convenience like every other ADVANCED name — but it is not a leak, and
`mf.window.Split` stays public. The prose contradicted the generated data; the
data was right.
```

## The four `Literal` aliases are API — measured, not assumed

`MetadataLevel`, `RegimeDirection`, `SamePeriodPolicy` and `StageDefaultScope` were
previously listed as needing "a yes/no rather than a rule". The rebuilt inventory
answers it: each is declared in its home submodule's `__all__`, and each appears in
a public signature.

| alias | home | used in |
|---|---|---|
| `MetadataLevel` | `mf.meta` | `configure`, `use_config` |
| `StageDefaultScope` | `mf.meta` | `configure`, `use_config` |
| `RegimeDirection` | `mf.data` | `define_regime` |
| `SamePeriodPolicy` | `mf.data` | `same_period_predictors` |

They are real submodule API types, not leaks. Their `__module__` reads `typing`
because a `Literal[...]` alias carries typing's module — which is why the inventory
treats `object.__module__` as corroboration rather than authority. They are
canonical public submodule types, they are ADVANCED, and they are not on the
removal list; only their top-level aliases are.

```{admonition} Correction (2026-08-09): `BoogingRegressor` is not a typo
:class: important

An earlier revision flagged `mf.BoogingRegressor` as reading like a typo for
"Boosting" and proposed confirming it before publication. Reading the source
settles it — it is **Booging**, the algorithm from Goulet Coulombe, *To Bag is to
Prune* (arXiv:2008.07063), and `model_ensemble/core.py:841` documents the mapping
to the paper's R function `Booging(y, X, X.new, ...)` line by line, including the
R defaults `B=100, mtry=0.8, sampling.rate=.75`.

It is correctly named, stays, and needs no decision. What it needs is a docs entry,
since `in_docs: false` in the inventory means a user meeting the name has nowhere
to look it up.

The lesson for this document: an unfamiliar name is a prompt to read the source,
not to propose a rename. Flagging a faithful implementation of a published
algorithm as a probable typo, inside a proposal to change the public API, is the
kind of error that costs the whole proposal credibility.
```

## How this inventory is built

`tools/api_inventory.py` resolves ownership from sources that declare it, in order:
the root `_LAZY_EXPORTS` map, the root `_LAZY_MODULES` tuple, each submodule's
`__all__`, and `object.__module__` as corroboration only. It separates three
surfaces — the 376 supported `__all__` names, the intentionally-public
`__version__`, and the three non-API root globals — because a stability decision
about the first should not be argued from a count that silently includes the third.

An earlier revision resolved an owner by scanning each submodule's `dir()` and
taking the first module that exposed the name. That produced two measurable errors:
it attributed the three stdlib globals to `mf.tests`, `mf.data` and `mf.evaluation`,
and — because its hard-coded module list omitted `analysis` — it reported
`axis_contribution` with no submodule home at all. Its canonical path is
`mf.analysis.axis_contribution`.

Corroboration, as measured: all 353 lazy exports appear in their home submodule's
`__all__`. `object.__module__` agrees with the declared home for 345 of 353; the
eight exceptions are structural rather than defects — three module-level constants
carry no `__module__`, the four `Literal` aliases report `typing`, and `Split`
reports `builtins`. The inventory records these exceptions instead of forcing an
invariant that the language does not support.

`python -m tools.api_inventory --check` fails on drift without rewriting the file.

## Release sequence

Not "delete 352 aliases". Three releases, in order:

**0.9.6 — publish the policy, remove the non-API globals.** This page ships as
the adopted tiers, with the canonical path for each symbol; the reference already
lists them. Separately and independently, `Any`, `annotations` and
`import_module` are removed from the root namespace. No deprecation period for
those three — they are not API, and removing them cannot break correct code.
Nothing else about the runtime changes.

**0.9.7 — warn on the 352 convenience aliases.** Each emits a `FutureWarning`
naming its canonical path: *"mf.random_forest is deprecated; use
mf.models.random_forest"*. This is where a user finds out, so the message carries
the fix. One release, and the canonical path it names is already documented,
because 0.9.6 shipped first.

**1.0 — remove the 352 aliases.** The root surface becomes the 25 names above.
Canonical submodule paths are untouched throughout: nothing in the ADVANCED or
EXPERIMENTAL tiers is removed by this sequence, only the second spelling of it.

The ordering is the point. The warnings cannot start before the docs give people
somewhere to move to, and the removal cannot land before a release in which the
warning was visible.

## What this page does not do

It changes no code. The alias `FutureWarning`s and the removal of the three
non-API globals are 0.9.6 and 0.9.7 work, tracked separately; publishing the
policy is step one precisely so that the later steps have something to point at.
