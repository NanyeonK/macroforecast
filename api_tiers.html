API stability tiers — proposal#

This is a proposal, not a change. Nothing here is implemented. Classifying 379 symbols is a decision about what the package promises to keep working, which is the author’s call; what follows is the evidence and a recommendation so that call is a short one.

Inventory: docs/api_inventory.json (generated by tools/api_inventory.py).

The finding that shapes everything else#

The documentation already teaches submodule paths, not top-level aliases. Every mf.* reference in README.md and docs/guide/getting_started.md:

from macroforecast.pipeline import Arm, EvalSpec, TargetSpec, pipeline_spec, run_pipeline

mf.configure
mf.data.load_fred_md
mf.window.from_cutoffs
mf.feature_engineering.feature_spec
mf.models.list_model_specs

Five submodule paths and one top-level name. Meanwhile dir(mf) exposes 379 public symbols, 347 of which are aliases for something that already has a submodule home.

So the canonical shape is not in dispute — it is already written down and taught. The top-level surface is what accumulated beside it.

Proposed tiers#

STABLE — the documented entry points#

mf.configure
mf.__version__

from macroforecast.pipeline import (
    Arm, TargetSpec, EvalSpec, pipeline_spec, run_pipeline,
    PipelineSpec, PipelineReport,
)
mf.data.load_fred_md
mf.data.custom_dataset
mf.window.from_cutoffs
mf.feature_engineering.feature_spec

Everything the getting-started path uses, plus the two spec/report types a caller necessarily touches. These get the full deprecation treatment: two minor releases and a FutureWarning before anything moves.

ADVANCED — public, canonical path is the submodule#

mf.models.*            mf.feature_engineering.*    mf.tests.*
mf.model_selection.*   mf.preprocessing.*          mf.output.*
mf.window.*            mf.evaluation.*             mf.forecasting.*

Documented in the generated reference, safe to use, and reached through their module. The top-level alias for each of these is the redundant part — not the function.

EXPERIMENTAL — contract still moving#

  • mf.interpretation.* — audited for the attribution primitives in #446, but anatomy, oshapley and the pipeline-level *_provider / precompute_* surfaces still have no oracles.

  • mf.reporting.* — no audit lane has covered it.

Usable; not covered by a stability promise until audited.

Three things to remove that are not decisions#

These are not API and never were:

Leaked re-exports of the standard library, surfaced because a submodule imported them at module scope. Removing them cannot break correct code, because no correct code calls mf.Any.

```{admonition} Correction (2026-08-09): Split was misclassified here :class: important

An earlier revision of this page listed mf.Split in the table above as “a builtin”. That was wrong, and the inventory this page is built from said so:

"name": "Split", "canonical": "mf.window.Split", "kind": "GenericAlias"

Split is a public type alias of the window subsystem. Whether the top-level alias is redundant is the same question as for every other ADVANCED name — but it is not a leak, and it is not removable without a deprecation cycle. The prose contradicted the generated data; the data was right.


Four more are `typing.Literal` aliases — `MetadataLevel`, `RegimeDirection`,
`SamePeriodPolicy`, `StageDefaultScope` — which **may** be intentional public
types. They need a yes/no rather than a rule.

```{admonition} Correction (2026-08-09): `BoogingRegressor` is not a typo
:class: important

An earlier revision flagged `mf.BoogingRegressor` as reading like a typo for
"Boosting" and proposed confirming it before publication. Reading the source
settles it — it is **Booging**, the algorithm from Goulet Coulombe, *To Bag is to
Prune* (arXiv:2008.07063), and `model_ensemble/core.py:841` documents the mapping
to the paper's R function `Booging(y, X, X.new, ...)` line by line, including the
R defaults `B=100, mtry=0.8, sampling.rate=.75`.

It is correctly named, stays, and needs no decision. What it needs is a docs entry,
since `in_docs: false` in the inventory means a user meeting the name has nowhere
to look it up.

The lesson for this document: an unfamiliar name is a prompt to read the source,
not to propose a rename. Flagging a faithful implementation of a published
algorithm as a probable typo, inside a proposal to change the public API, is the
kind of error that costs the whole proposal credibility.

A caveat on how this inventory was built#

tools/api_inventory.py resolves an owner by scanning each submodule’s dir() and taking the first module that exposes the name. That misattributes an imported helper or an accidental module global — which is exactly how Any, annotations and import_module show up owned by mf.tests, mf.data and mf.evaluation rather than by the standard library.

For the three leaked names that is harmless, because they are being removed either way. For any decision that turns on which submodule owns a symbol, the inventory should first be rebuilt from authoritative sources — the root _LAZY_EXPORTS, each submodule’s __all__, and object.__module__ — rather than from dir() order.

Proposed deprecation map#

Not “delete 347 aliases”. In order:

  1. Publish the tiers in the guide, with the canonical path for each symbol. No code changes; the reference already lists them.

  2. Remove the four leaked non-API names. No deprecation period — they are not API.

  3. Emit FutureWarning on top-level ADVANCED aliases, naming the canonical path: “mf.random_forest is deprecated; use mf.models.random_forest”. One release. This is where a user finds out, and the message has to carry the fix.

  4. Remove the aliases one release later.

Steps 3 and 4 are the breaking part and should not start until 1 and 2 have shipped, so anyone reading the docs has somewhere to move to before the warnings begin.

What would make this decidable#

Two questions, and the rest follows mechanically:

  1. Is the top-level alias surface supported, or convenience? If supported, 379 symbols enter the semantic-versioning contract at 1.0 and steps 3-4 never happen. If convenience, they get the deprecation cycle above.

  2. Do the four Literal aliases belong in the public API? If yes they are STABLE types; if no they join the removal in step 2.
