API stability tiers — proposal#

This is a proposal, not a change. Nothing here is implemented. Classifying the 376 names in mf.__all__, plus the intentionally-public mf.__version__, is a decision about what the package promises to keep working, which is the author’s call; what follows is the evidence and a recommendation so that call is a short one.

Inventory: docs/api_inventory.json (generated by tools/api_inventory.py).

The split is deliberate: the inventory supplies facts, this page supplies policy. docs/api_inventory.json records only what the package declares — which submodule owns a name, whether it is a lazy export or a namespace, and whether the entry docs reference it. It assigns no tier. The tiers below are a proposal about what the package should promise, which is a judgement no generator can make.

The finding that shapes everything else#

The documentation already teaches submodule paths, not top-level aliases. Every mf.* reference in README.md and docs/guide/getting_started.md:

from macroforecast.pipeline import Arm, EvalSpec, TargetSpec, pipeline_spec, run_pipeline

mf.configure
mf.__version__
mf.data.load_fred_md
mf.window.from_cutoffs
mf.preprocessing.preprocess_spec
mf.feature_engineering.feature_spec
mf.feature_engineering.marx_step
mf.models.list_model_specs

Six mf.<submodule>.<name> paths and a macroforecast.pipeline import — against two top-level names, mf.configure and mf.__version__, both of which the proposal already treats as STABLE. Meanwhile mf.__all__ exports 376 supported names — 353 lazy exports, every one of which already has a submodule home, plus the 23 submodule namespaces themselves. (dir(mf) reports 379; the extra three are not API and are separated out below.)

So the canonical shape is not in dispute — it is already written down and taught. The top-level surface is what accumulated beside it.

Proposed tiers#

STABLE — the documented entry points#

mf.configure
mf.__version__

from macroforecast.pipeline import (
    Arm, TargetSpec, EvalSpec, pipeline_spec, run_pipeline,
    PipelineSpec, PipelineReport,
)
mf.data.load_fred_md
mf.data.custom_dataset
mf.window.from_cutoffs
mf.feature_engineering.feature_spec

Everything the getting-started path uses, plus the two spec/report types a caller necessarily touches. These get the full deprecation treatment: two minor releases and a FutureWarning before anything moves.

ADVANCED — public, canonical path is the submodule#

mf.models.*            mf.feature_engineering.*    mf.tests.*
mf.model_selection.*   mf.preprocessing.*          mf.output.*
mf.window.*            mf.evaluation.*             mf.forecasting.*

Documented in the generated reference, safe to use, and reached through their module. The top-level alias for each of these is the redundant part — not the function.

EXPERIMENTAL — contract still moving#

  • mf.interpretation.* — audited for the attribution primitives in #446, but anatomy, oshapley and the pipeline-level *_provider / precompute_* surfaces still have no oracles.

  • mf.reporting.* — no audit lane has covered it.

Usable; not covered by a stability promise until audited.

Three non-API globals to remove — not a decision#

These are not API and never were:

symbol

actually

bound by

mf.Any

typing.Any

from typing import Any

mf.annotations

__future__.annotations

from __future__ import annotations

mf.import_module

importlib.import_module

from importlib import import_module

All three are globals of macroforecast/__init__.py itself — imports the lazy loader needs at root module scope. They are public in dir(mf), absent from __all__, and owned by no submodule. Removing them cannot break correct code, because no correct code calls mf.Any.

An earlier revision of this page said they were “surfaced because a submodule imported them at module scope”, and attributed them to mf.tests, mf.data and mf.evaluation. That was the old dir()-scanning inventory misreporting their provenance; the rebuilt inventory records them as root globals.

```{admonition} Correction (2026-08-09): Split was misclassified here :class: important

An earlier revision of this page listed mf.Split in the table above as “a builtin”. That was wrong, and the inventory this page is built from said so:

"name": "Split", "canonical": "mf.window.Split", "kind": "GenericAlias"

Split is a public type alias of the window subsystem. Whether the top-level alias is redundant is the same question as for every other ADVANCED name — but it is not a leak, and it is not removable without a deprecation cycle. The prose contradicted the generated data; the data was right.


## The four `Literal` aliases are API — measured, not assumed

`MetadataLevel`, `RegimeDirection`, `SamePeriodPolicy` and `StageDefaultScope` were
previously listed as needing "a yes/no rather than a rule". The rebuilt inventory
answers it: each is declared in its home submodule's `__all__`, and each appears in
a public signature.

| alias | home | used in |
|---|---|---|
| `MetadataLevel` | `mf.meta` | `configure`, `use_config` |
| `StageDefaultScope` | `mf.meta` | `configure`, `use_config` |
| `RegimeDirection` | `mf.data` | `define_regime` |
| `SamePeriodPolicy` | `mf.data` | `same_period_predictors` |

They are real submodule API types, not leaks. Their `__module__` reads `typing`
because a `Literal[...]` alias carries typing's module — which is why the inventory
treats `object.__module__` as corroboration rather than authority. Whether the
*top-level* alias is redundant is the same open question as for every other
ADVANCED name; they do not join the removal list.

```{admonition} Correction (2026-08-09): `BoogingRegressor` is not a typo
:class: important

An earlier revision flagged `mf.BoogingRegressor` as reading like a typo for
"Boosting" and proposed confirming it before publication. Reading the source
settles it — it is **Booging**, the algorithm from Goulet Coulombe, *To Bag is to
Prune* (arXiv:2008.07063), and `model_ensemble/core.py:841` documents the mapping
to the paper's R function `Booging(y, X, X.new, ...)` line by line, including the
R defaults `B=100, mtry=0.8, sampling.rate=.75`.

It is correctly named, stays, and needs no decision. What it needs is a docs entry,
since `in_docs: false` in the inventory means a user meeting the name has nowhere
to look it up.

The lesson for this document: an unfamiliar name is a prompt to read the source,
not to propose a rename. Flagging a faithful implementation of a published
algorithm as a probable typo, inside a proposal to change the public API, is the
kind of error that costs the whole proposal credibility.

How this inventory is built#

tools/api_inventory.py resolves ownership from sources that declare it, in order: the root _LAZY_EXPORTS map, the root _LAZY_MODULES tuple, each submodule’s __all__, and object.__module__ as corroboration only. It separates three surfaces — the 376 supported __all__ names, the intentionally-public __version__, and the three non-API root globals — because a stability decision about the first should not be argued from a count that silently includes the third.

An earlier revision resolved an owner by scanning each submodule’s dir() and taking the first module that exposed the name. That produced two measurable errors: it attributed the three stdlib globals to mf.tests, mf.data and mf.evaluation, and — because its hard-coded module list omitted analysis — it reported axis_contribution with no submodule home at all. Its canonical path is mf.analysis.axis_contribution.

Corroboration, as measured: all 353 lazy exports appear in their home submodule’s __all__. object.__module__ agrees with the declared home for 345 of 353; the eight exceptions are structural rather than defects — three module-level constants carry no __module__, the four Literal aliases report typing, and Split reports builtins. The inventory records these exceptions instead of forcing an invariant that the language does not support.

python -m tools.api_inventory --check fails on drift without rewriting the file.

Proposed deprecation map#

Not “delete 353 aliases”. In order:

  1. Publish the tiers in the guide, with the canonical path for each symbol. No code changes; the reference already lists them.

  2. Remove the three non-API globals. No deprecation period — they are not API.

  3. Emit FutureWarning on top-level ADVANCED aliases, naming the canonical path: “mf.random_forest is deprecated; use mf.models.random_forest”. One release. This is where a user finds out, and the message has to carry the fix.

  4. Remove the aliases one release later.

Steps 3 and 4 are the breaking part and should not start until 1 and 2 have shipped, so anyone reading the docs has somewhere to move to before the warnings begin.

What would make this decidable#

One question is genuinely open, and the rest follows mechanically.

Is the top-level alias surface supported, or convenience? If supported, the 376 names in mf.__all__ enter the semantic-versioning contract at 1.0 and steps 3-4 never happen. If convenience, they get the deprecation cycle above.

The question this page used to pair it with — whether the four Literal aliases belong in the public API — is answered above from the rebuilt inventory: each is declared in its home submodule’s __all__ and used in a public signature, so they follow the same rule as every other ADVANCED name. It is no longer a decision.
